# DECISIONS — принятые решения

Формат: дата · тема · решение · почему.

- **2026-11-04 · Service Worker и APP_NAME.** `public/sw.js` остаётся статичным файлом и подгружает `/sw-config.js` (`importScripts`), который отдаёт `APP_NAME` из `src/config/app.ts`. Так имя продукта меняется в одном месте, а SW не нужно собирать.
- **2026-11-04 · Playwright.** `@playwright/test@1.63.0` совпадает с предустановленным Chromium; в контейнере используется `/opt/pw-browsers/chromium`, в CI — стандартная установка. E2E всегда в демо-режиме (`NEXT_PUBLIC_DEMO_MODE=1`).
- **2026-11-04 · CI.** GitHub Actions собирает в демо-режиме (без секретов), E2E в CI пока не запускается (нужна установка браузеров, долго) — запускается локально `npm run test:e2e`.
- **2026-11-04 · Тёмная тема без переписывания разметки.** Старые классы (`bg-card`, `bg-surface`, `text-muted`, `bg-accent-soft`…) переназначены на тёмные токены из `design/DESIGN.md`; добавлены `surface-3`, `ink-2`, `accent-2` (#7E9BB3), `link` (#9DB6CB), `review/-soft`. `danger` = светло-красный текст #F0B2AC, `danger-soft` = фон #4A2E2D. `text-accent` заменён на `text-link` (контраст на тёмном фоне).
- **2026-11-04 · Элементы раскладки, которым нужны новые данные** (KPI «На проверке» и «Сейчас на смене», поиск Ctrl+K, лента событий, канбан, календарь «день» и drag&drop, плашка приёмки, фото до/после, аватарки, карточка смены у сотрудника, карточка пробного периода) делаются вместе со своей функцией в этапах 2, 3, 9, 11 — иначе пришлось бы рисовать пустые заглушки.
- **2026-11-04 · Шрифты PDF.** Статические TTF Golos Text 400/600 и Geologica 600 из Google Fonts (OFL) в `assets/fonts`, проверено наличие кириллицы, ß, умлаутов и €.
- **2026-11-04 · Начисление по дате приёмки.** И часы, и фикс по задаче попадают в период по `accepted_at` (а не по дате записи времени). Так суммы недели/месяца, Excel и PDF совпадают и ничего не начисляется до приёмки. До приёмки сотрудник видит сумму как «Ждёт приёмки».
- **2026-11-04 · Задача «На проверке» не считается просроченной** — работа сдана, ход за начальником.
- **2026-11-04 · Свои статусы.** `task_statuses` (5 системных на фирму создаёт триггер при создании фирмы). Задача хранит этап `status` + необязательный `custom_status_id`; выбор своего статуса переводит задачу в его этап, смена этапа сбрасывает несовпадающий свой статус (триггер).
- **2026-11-04 · Авто-приёмка** выполняется сервис-ролью в `/api/cron/frequent`; `accepted_by = null` означает «принято автоматически». Напоминание начальнику — за сутки до авто-приёмки, один раз.
- **2026-11-04 · pg_cron.** Миграция только создаёт функции `private.enable_frequent_cron(url, secret)` / `disable_frequent_cron()`; расписание включается вручную одной SQL-командой (README), без настроек ничего не запускается.
- **2026-11-04 · Фото при возврате на доработку** прикладывается через обычный блок «Фото» задачи (отдельная загрузка в форме возврата — позже, вместе с фото до/после в этапе 11).
- **2026-11-04 · Демо-фирма (пункт E).** Уникальность `members.user_id` заменена двумя частичными индексами: максимум одна реальная (`is_demo=false`) и одна демо-фирма на пользователя. Активная фирма — `user_settings.active_member_id`; `private.current_member_id()` выбирает её, а `my_member_id/my_firm_id/is_boss` строятся на ней. «Как работник» — `user_settings.acting_member_id`, учитывается только если активная фирма демо, пользователь там начальник, а цель — демо-сотрудник без логина (`user_id null`). Всё переключение только через RPC (`switch_firm`, `set_acting`), прямой записи в `user_settings` нет.
- **2026-11-04 · Демо-фирма создаётся** при регистрации фирмы (`create_firm` → `create_demo_firm`) и лениво кнопкой «Демо-фирма» в онбординге. Данные — `private.seed_demo_firm` (следующие этапы дополняют её через `create or replace`). Push демо-участникам не отправляется.
- **2026-11-04 · Демо-режим без Supabase** (`NEXT_PUBLIC_DEMO_MODE`): «Смотреть как» = вход под другой тестовой персоной (cookie), т. к. в памяти нет второй фирмы.
- **2026-11-04 · После пробного периода** блокируются только вставки (RLS `firm_can_write` + `assertWritable` на сервере): задачи, сотрудники, приглашения, шаблоны, группы, статусы, заявки, чек-листы, комментарии, фото, записи времени. Изменение и чтение остаются, чтобы можно было закрыть текущую работу и выгрузить данные. Продлевать/менять тариф может только service role (суперадмин), это проверяет триггер.
- **2026-11-04 · Тарифы.** Цены — плейсхолдер `[ЦЕНА]` в `DEFAULT_PLANS`, в этапе 7 переедут в БД (суперадминка). Оплата — интерфейс `PaymentProvider` + `StubPaymentProvider`, «Оплатить» ведёт на страницу «Оплата скоро будет доступна». Контакт — `CONTACT_MAILTO` (плейсхолдер в `src/components/trial/trial.tsx`).
- **2026-11-04 · Онбординг.** После регистрации — `/boss/welcome` (3 шага + демо + установка). Дашборд перенаправляет туда, пока не нажато «Начать» (`user_settings.onboarding_done`). Подсказки закрываются навсегда (`hints_dismissed`).
- **2026-11-04 · Вход по коду на сервере (пункт D).** `requestCode`/`verifyCode` — server actions; браузер больше не вызывает Supabase Auth напрямую. Лимиты: запрос кода 5/ч на e-mail и 20/ч на IP, проверка — 5 попыток за 15 мин на e-mail. Ответ не раскрывает, существует ли e-mail.
- **2026-11-04 · Rate limit** — таблица `private.rate_limits` + `public.rate_limit_hit` (фиксированное окно), вызывать может только service role. IP хранится только как SHA-256 с солью. Если БД недоступна — запрос пропускается (не блокируем вход из-за сбоя лимитера). В демо-режиме лимиты в памяти.
- **2026-11-04 · CSP.** Nonce + `strict-dynamic` для скриптов; для стилей `'unsafe-inline'`, т. к. React использует атрибуты `style`. Разрешены: свой домен, Supabase (https/wss), тайлы карты, Sentry, Turnstile. `/api/*` не проходит через proxy (JSON, CSP не нужен; сессию обновляют сами route handlers).
- **2026-11-04 · Чужая задача у сотрудника** показывает «не найдено», но HTTP-статус может быть 200 из-за стриминга (`loading.tsx`). Содержимое при этом не отдаётся — проверено E2E.
- **2026-11-04 · Повторный ввод кода** (`requireRecentAuth`, 10 минут) — для смены роли сотрудника; в этапе 5 добавится к удалению фирмы и полной выгрузке. Время последнего подтверждения — `user_settings.reauth_at` (пишет только сервер). Выход после бездействия — 12 ч без активности (клиентский таймер на все вкладки); для жёсткого серверного лимита — настройка «Inactivity timeout» в Supabase Auth (README).
- **2026-11-04 · Sentry без SDK.** Лёгкая отправка событий через `instrumentation.ts` → `onRequestError` (envelope API); e-mail, UUID и IP вычищаются, заголовки/cookies/тело не отправляются. Без `SENTRY_DSN` — выключено.
- **2026-11-04 · npm audit.** High/critical устранены (Vitest 5). Остались moderate: `uuid` внутри `exceljs` (уязвимость только при передаче `buf` в v3/v5/v6 — exceljs так не делает) и `minimatch` в dev-инструментах ESLint.
- **2026-11-04 · Проверка бандла.** `npm run check:bundle` (и в CI) ищет имена и значения серверных секретов в `.next/static`.
- **2026-11-04 · Правовые тексты** — шаблоны в `src/legal/content.ts` (DE обязательна, RU — информационная), плейсхолдеры `[ИМЯ / FIRMA]`, `[АДРЕС]`, `[EMAIL]`, `[ТЕЛЕФОН]`, `[USt-IdNr]`, `[HANDELSREGISTER]` и т. д. Тексты — заготовка, их нужно проверить у юриста (LAUNCH_CHECKLIST). Версия текста `LEGAL_VERSION` сохраняется вместе с каждым согласием.
- **2026-11-04 · Cookie-баннер** — только информирование (используются лишь необходимые cookies, выбора нет). Подтверждение хранится на устройстве (версия + дата) и, если пользователь вошёл, в `consents`.
- **2026-11-04 · Выгрузка фирмы** — ZIP (fflate): JSON по каждой таблице + до 300 фото, токены приглашений не выгружаются. Требует подтверждения кодом за последние 15 минут. Сотрудник выгружает свои данные JSON без финансов фирмы.
- **2026-11-04 · Удаление фирмы** — название + повторный код → `deletion_scheduled_for = +30 дней`, отмена в любой момент; ежедневный cron удаляет фирму (каскадом) и её фото. Счета (этап 16) будут храниться отдельно 10 лет.
- **2026-11-04 · Запрос сотрудника на удаление** создаёт `data_requests`; начальник видит его в настройках и закрывает после удаления сотрудника (кнопка «Удалить» в карточке сотрудника сразу отзывает доступ).
- **2026-11-04 · Лендинг.** Тексты — `src/landing/content.ts` (DE/RU по макету Landing), в БД `site_content(key='landing', locale)` можно переопределить любые ключи (JSON, редактирование — суперадминка, этап 7). Цены — таблица `plans` (`price_cents null` → показывается `[ЦЕНА]`). Язык лендинга — `?lang=de|ru` (для hreflang нужны разные URL), иначе cookie/заголовок браузера. Вместо скриншота — лёгкая HTML-вёрстка «превью дашборда» (не нужно обновлять картинку при изменении дизайна).
- **2026-11-04 · Отзывы.** Таблица `reviews` (заполняется со ссылки заказчика, этап 10) с `allow_publish` и модерацией; публично отдаются только `approved + allow_publish`, не из демо-фирм, только имя без фамилии — через RPC `published_reviews`. Нет таких отзывов — блок не показывается.
- **2026-11-04 · SEO.** sitemap/robots/OG-картинка (шрифты Geologica/Golos из assets), noindex для `/boss`, `/staff`, `/join`, `/onboarding`, `/login`, тарифов; в robots.txt закрыты приватные пути и `/c/` (ссылки заказчика).
- **2026-11-04 · Суперадмин.** Доступ — e-mail текущего пользователя в `SUPERADMIN_EMAILS`, проверка на сервере в layout и в каждом действии; иначе 404 (раздел не раскрывается). Данные — только через service role на сервере. В демо-режиме суперадмин — `chefin@demo.de`, чтобы экраны можно было посмотреть. Все действия пишутся в `admin_audit`.
- **2026-11-04 · Фича-флаги.** `feature_flags` (глобальный default) + `firm_features` (переопределение для фирмы, `set_by = admin|boss`). Если админ закрепил значение (`set_by='admin'`), начальник не может его изменить (RLS). Сервер проверяет флаги в действиях и маршрутах (`assertFeature`), меню скрывает выключенные разделы. Флаги для фич будущих этапов заведены заранее (geolocation, invoices, public_form по умолчанию выключены).
- **2026-11-04 · Тексты лендинга в админке** — JSON-редактор по языкам; сохраняются только известные ключи верхнего уровня, вложенные объекты сливаются со стандартными.
- **2026-11-04 · Логотип** — публичный бакет `firm-logos` (только PNG/JPG/WebP, ≤ 512 КБ), писать может только начальник своей фирмы (политика по первой папке пути = firm_id). Публичный, т. к. логотип показывается на ссылке заказчика без входа. Загрузка через server action (сервер проверяет тип и размер).
- **2026-11-04 · Видимые поля задачи** — `firms.task_fields` (jsonb); скрывают поля в форме и блок фото в карточке. Данные в скрытых полях не удаляются.
- **2026-11-04 · «Выйти со всех устройств»** — `auth.signOut({ scope: "global" })` (Supabase отзывает все refresh-токены) + запись в журнал входов.
- **2026-11-04 · Прибыль с расходами.** Прибыль = цена клиента − оплата труда (фикс + часы + смены + премии/вычеты) − одобренные расходы задач, принятых в периоде. Расход с галочкой «вернуть сотруднику» добавляется к его заработку (`reimburseCents`), но не к оплате труда — двойного учёта нет. В Excel чеки — ссылкой на задачу в приложении (нужен вход), а не публичной ссылкой на файл: подписанные ссылки живут ≤ 15 минут.
- **2026-11-04 · Смены.** `shifts` с паузами (`break_minutes` + `break_started_at`), максимум одна открытая смена на сотрудника (уникальный индекс), id от клиента → офлайн-очередь идемпотентна (`shift_start/pause/resume/end` через `/api/sync`). Почасовая оплата — по задачам ИЛИ по сменам (`members.hourly_basis`), ставка фиксируется в записи (триггер). Смена оплачивается по дате окончания, не ждёт приёмки задач. Забытая смена закрывается в `/api/cron/frequent` через `firms.shift_autoclose_hours` (по умолчанию 12) с меткой «проверить».
- **2026-11-04 · Arbeitszeiterfassung.** Удаления смен и записей времени нет ни у кого (политики DELETE нет). Закрытые записи меняются только через RPC `edit_time_record` — начальник, обязательная причина, старое/новое в `time_edits`; сотрудник видит свои записи и историю (`/staff/times`).
- **2026-11-04 · Премии/вычеты** не редактируются и не удаляются — исправление делается обратной записью (прозрачно для сотрудника).
- **2026-11-04 · Автоназначение** — сотрудник с наименьшим числом открытых задач на выбранную дату, без отпуска/больничного. У задачи нет своей группы, поэтому фильтр по группе в функции есть (`groupId`), но в форме пока не используется.
- **2026-11-04 · Ссылка заказчика.** Токен 32 байта (64 hex), отзыв = пометка `revoked`, «пересоздать» отзывает старые. Данные отдаёт только сервер через service role после проверки токена (не отозван, не истёк) и только по этой задаче; лимит запросов по IP; `noindex` + запрет в robots.txt. Заказчик может принять работу только в статусе «На проверке» (`accepted_via = 'client'`). Отзыв — один на задачу, модерация в суперадминке, согласие на публикацию записывается в `consents` с версией текста. Цена скрывается флагом клиента `hide_price`.
- **2026-11-04 · Публичная форма** `/f/[slug]` работает только при включённом флаге `public_form` (по умолчанию выключен) и заданном адресе. Защита: honeypot-поле, подписанная HMAC метка времени (форма должна быть открыта ≥ 3 с и ≤ 2 ч), лимит 5/ч на IP, Turnstile при наличии ключей.
- **2026-11-04 · Почта** — минимальный модуль `src/lib/email` (Brevo HTTP API, сервер в ЕС; без ключа пишет в лог только тему). Письмо с просьбой об отзыве уходит после приёмки начальником или авто-приёмки, если у клиента есть e-mail, фирма не демо и отзыва ещё нет. Остальные письма — этап 12.
- **2026-11-04 · Фото «до/после»** — колонка `task_photos.kind`, выбор типа перед загрузкой; ссылка заказчика показывает до/после, а если их нет — обычные фото.
- **2026-11-04 · README и LAUNCH_CHECKLIST написаны раньше этапа 18**, т. к. без них нельзя развернуть уже готовые этапы 0–10, а сессия может прерваться. При следующих этапах их нужно дополнять (новые переменные, бакеты, cron-задачи).
- **2026-11-04 · Drag & drop без библиотек.** Канбан и календарь используют pointer events (одинаково для мыши и пальца, `touch-action: none` на карточке), цель определяется через `elementFromPoint` по `data-col` / `data-day`; изменение сразу видно (оптимистично) и откатывается при ошибке сервера.
- **2026-11-04 · Канбан.** Колонки = статусы фирмы; перенос в системную колонку меняет этап, в свою — ставит `custom_status_id` (этап берётся из статуса). Выполненные задачи показываются за последние 14 дней.
- **2026-11-04 · Поиск** — RPC `search_all` с `security invoker`: работает под RLS пользователя, поэтому сотрудник находит только свои задачи и заявки, а клиентов и людей видит только начальник. Полнотекст по задачам (`to_tsvector('simple')`, префиксы — подходит для DE и RU), по людям/клиентам/заявкам — `ilike`.
- **2026-11-04 · Лента событий** пишется триггерами (`activity`): смена статуса, начало/конец смены, расход, заявка, отзыв, комментарий. Видна только начальнику.
- **2026-11-04 · @упоминания** — `@Имя` или `@Имя Фамилия`; уведомление получают только те, кто видит задачу (начальники и исполнитель), автор исключается.
- **2026-11-04 · Напоминание за час** — `/api/cron/frequent` (каждые 15 мин) отправляет push исполнителю за ≤ 75 мин до срока для задач с указанным временем, один раз (`reminder_sent_at`; сбрасывается при смене срока).
- **2026-11-04 · Типы уведомлений** — `notification_prefs` (по умолчанию всё включено, хранится только выключенное). Фильтр в `sendPushToMembers(…, type)`. О новой задаче сотрудник уведомляется всегда (требование ТЗ), переключателя нет. Типы «отпуск» и «обмен сменами» заведены заранее для этапа 14.
- **2026-11-04 · Офлайн-файлы** — IndexedDB (`app-offline/files`): фото и расходы с чеком сохраняются целиком (Blob) и отправляются при появлении сети вместе с обычной очередью. Id записи = имя файла в хранилище (`upsert`) → повторная отправка не создаёт дублей фото.
- **2026-11-04 · Письма** — ежедневный cron: «пробный период заканчивается» (один раз при ≤ 3 днях) и недельная сводка по понедельникам. Приглашение по e-mail — из панели приглашений (с лимитом).
- **2026-11-04 · Пагинация** — «Показать ещё» через параметр `limit` (+50): архив, клиенты, выполненные задачи сотрудника, лента событий (+25).
- **2026-11-04 · Геометка.** Функция `geolocation` (по умолчанию выключена) включается начальником. Позиция берётся только в момент «Начал/Закончил» и начала/конца смены (`getCurrentPosition`, 4 с), фоновой слежки нет. Без согласия сотрудника запись невозможна на уровне БД (RLS проверяет последнее согласие `consents.kind='geolocation'`); отзыв согласия — в профиле.
